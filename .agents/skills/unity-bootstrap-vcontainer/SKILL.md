# Bootstrap → Gameplay с VContainer

Создай переносимую основу из [assets/template](assets/template), без игровых механик. Ожидаемый результат: Bootstrap автоматически открывает Gameplay; Gameplay можно запускать напрямую; перезапуск пересоздаёт её контейнер, сохраняя корень и навигатор.

## Жизненным циклом управляет VContainer

- У App и Gameplay включён `autoRun`. Не переопределяй `Awake`, не выключай Auto Run в runtime, не добавляй собственные `Initialize/Build` и не назначай `parentReference` из загрузчика. Project root и родителя сценового scope определяет VContainer через `VContainerSettings`.
- `BootstrapEntryPoint : IStartable` зарегистрирован в App. Отдельный Bootstrap scope не нужен. Навигатор из prefab зарегистрирован в App как persistent singleton; он вызывает обычный `LoadSceneAsync(..., Single)` и защищает от двойного запроса.
- Инициализацию сценовых сервисов регистрируй в Gameplay через штатные entry points VContainer. Не вводи состояния загрузчика, ручную готовность контейнера, UniTask или `EnqueueParent` ради обычного перехода между этими сценами.
- Прямой запуск Gameplay — обязательный сценарий, а не ошибка конфигурации. Root entry point проверяет активную сцену и не перенаправляет Gameplay в Bootstrap.

## Перед применением

1. Прочитай инструкции целевого проекта, состояние Git, Unity version, manifest и lock. Для анализа существующего кода используй CodeGraph, если этого требует проект. В новом проекте отсутствие собственного кода не мешает установке.
2. Нужны подключённый Unity MCP, VContainer, Eflatun.SceneReference и Unity Test Framework. Базовая совместимость шаблона сверена по API Unity `6000.3.18f1`, VContainer `1.19.0`, Eflatun `5.0.0`, Test Framework `1.6.0`; запуск в отдельном чистом проекте ещё не подтверждён. Сопоставь версии через Context7 и официальные источники. Не обновляй существующие зависимости автоматически. Если чего-то нет, сначала сообщи о недостающем пакете; установку согласуй в рамках запроса, не ставь DOTween, UniTask, TMP или Addressables ради этой базы.
3. Применение скилла с просьбой создать основу разрешает работу через Unity MCP со сценами, prefab и указанными настройками. Оно не разрешает запуск Play Mode/тестов вопреки инструкциям проекта: создание тестов и их выполнение — разные действия. Для запроса только на анализ ничего не создавай.
4. Через ресурсы MCP проверь `mcpforunity://custom-tools`, `mcpforunity://instances`, `mcpforunity://editor/state`, `mcpforunity://project/info`. При нескольких Editor выбери экземпляр по полному пути проекта и закрепи его. Проверь отсутствие Play Mode, ошибок компиляции и несохранённых сцен. Не закрывай диалоги и не сохраняй чужие изменения автоматически.
5. Проверь существующие Bootstrap/Gameplay, Scope'ы, VContainerSettings, Preloaded Assets, build scene list и активный Build Profile. При обычной установке существующую архитектуру не заменяй. При явно запрошенном приведении существующего Bootstrap используй раздел ниже. При другой корневой конфигурации останови зависимые действия и покажи конфликт. Пустая SampleScene может остаться в конце списка сборки.

Прочитай [references/architecture.md](references/architecture.md) перед изменением схемы. Оставь стандартные имена и namespace `ProjectBootstrap`, если пользователь не задал другие. Это не генератор произвольной архитектуры.

## Создание через Unity MCP

1. Сопоставь дерево `assets/template/Assets` с `<project>/Assets`. Копируй исходники и asmdef с сохранением относительных путей, без `.meta` из исходного проекта. Создание текстовых файлов допустимо файловыми инструментами, если это разрешено средой. Уже идентичные файлы пропускай; отличающиеся не перезаписывай. До копирования проверь всё дерево, чтобы не оставить половину файлов из-за поздней коллизии. Unity генерирует новые GUID.
2. Если файлы записаны вне MCP, запроси один refresh/import через MCP. Дождись завершения компиляции и domain reload, прочитай Console. После ошибки не пытайся добавлять ещё не скомпилированные компоненты.
3. Найди в актуальном `mcpforunity://menu-items` пункт `Tools/Project Bootstrap/Install Bootstrap and Gameplay`. Выполни его через `execute_menu_item`. Он вызывает поставляемый `BootstrapSceneInstaller`, который средствами Unity Editor создаёт сцены, prefab и ссылки Inspector, VContainerSettings, запись Preloaded Assets и порядок сцен. Не создавай YAML или GUID вручную. Если меню отсутствует, сначала проверь импорт, asmdef и Console.
4. Прочитай результат команды и Console. Само `execute_menu_item` может успешно отправить команду, даже если Editor-код сообщил ошибку. Установщик отказывается перезаписывать артефакты: при полной существующей базе только сообщает об этом, при частичной — останавливается. После частичного сбоя перечисли созданные пути и причину; исправляй только подтверждённые дефекты, без автоматического удаления или бесконечного повторного запуска.
5. Через MCP прочитай созданные объекты/ассеты и настройки. Проверь ссылки навигатора на обе сцены, App scope → prefab навигатора, Settings → prefab App scope, Settings в Preloaded Assets, `autoRun=true`, пустой явный Parent у Scope'ов. В Bootstrap нет scene instance App scope; в Gameplay ровно один Gameplay scope. Установщик сохраняет прежние Preloaded Assets и остальные сцены.
6. В Unity 6 проверь фактический список сцен активного Build Profile: при переопределении глобального списка установка `EditorBuildSettings.scenes` недостаточна. Согласуй список профиля с Bootstrap первым и Gameplay вторым через поддерживаемые MCP/Editor API; если доступа нет, передай это как точное ручное действие и оставь проверку сборки неподтверждённой. Не меняй платформу и прочие параметры профиля.

Сцены/ассеты создаются через Editor-установщик, вызванный MCP; не обходи недоступный MCP ручной записью сериализованных Unity-файлов. Установщик создаёт в обеих сценах стандартные Camera и Directional Light без зависимости от render pipeline. Визуальную настройку 2D/3D выполняют отдельно.

## Приведение существующего Bootstrap по прямому запросу

Не запускай установщик новой основы поверх существующих сцен. Сначала проследи зависимости старого запуска, затем адаптируй шаблон к namespace и asmdef проекта. Сохрани игровые регистрации, каталог, Inspector-ссылки, объекты сцен, пути и GUID существующих assets. Не добавляй диагностический probe, если проекту он не нужен: проверки освобождения выполняет test-only `IDisposable`.

Перенеси стартовый entry point в App, создай/подключи persistent navigator prefab. Через Unity Editor API включи `autoRun` у Gameplay и очисти его явный Parent. Удали только устаревший Bootstrap scope-компонент, сохранив его GameObject и пользовательские компоненты. После отвязки убери старый загрузчик, ручные методы сборки и их вызовы. Если сохранённые сцены ещё ссылаются на удаляемый тип, сначала мигрируй компоненты, затем удаляй скрипт вместе с его `.meta`.

Команда миграции должна останавливаться перед несохранёнными сценами и конфликтующими ссылками; при повторном запуске уже корректная база остаётся без изменений. Обнови тесты и документацию под прямой Gameplay, автоматический parent и настоящий restart через навигатор. Не переноси старые тесты ручного `Build` как рабочий контракт новой схемы.

После успешной миграции удали временные проектные setup/validator-команды и вспомогательные runtime-классы, которые обслуживали только старую схему. Проверки сохранённой конфигурации оставь в EditMode-тестах; установщик нового проекта в шаблоне скилла сохраняется.

## Проверка и отчёт

- Минимальная обязательная проверка установки: Console без новых ошибок, прочитанные связи и настройки, корректные asmdef. При разрешённом запуске тестов выполни только `ProjectBootstrap.Tests.EditMode.BootstrapConfigurationTests` и `ProjectBootstrap.Tests.PlayMode.BootstrapLifecycleTests`; дождись результата test job. Не запускай весь проектный набор без необходимости.
- EditMode проверяет ссылки prefab, root settings/preload, порядок сцен, единственный Gameplay scope и повторную установку без изменения ассетов/GUID/настроек. PlayMode проверяет зарегистрированный entry point, защиту от двойного запроса, parent/resolve, перезапуск и освобождение старого контейнера, уничтожение scoped-сервиса и прямую загрузку Gameplay при живом root. Первый автоматический dispatch и холодное создание root проверяются вручную: тестовый runner может создать корень до начала теста. Тесты создают временные тестовые регистрации; игровых сервисов в runtime нет.
- Для ручной приёмки: Play из Bootstrap → Gameplay; Play напрямую из Gameplay → один root и один navigator, без перенаправления в Bootstrap; Stop/Play повторно → нет дубликатов. Проверить с обычными настройками Enter Play Mode; если проект использует отключённый Domain Reload, повторить с его реальными настройками. После перезапуска Gameplay root сохраняется, старый scene scope освобождается, новый создаётся. Перезапуск проверяется поставляемым PlayMode-тестом, без добавления временного UI в продукт.
- Отдельно требуется запуск development build: первая сцена Bootstrap автоматически переходит в Gameplay без Editor API и ошибок карт Eflatun. Не объявляй эту проверку пройденной по результату Editor-тестов.
- Сообщи созданные пути, версии, что проверено инструментально, результаты разрешённых тестов и оставшиеся ручные действия. Не объявляй неподтверждённые Unity-поведение или сборку проверенными.

Не включай в основу gameplay, input, UI, адресуемые ресурсы, tweening, сохранения или универсальный scene router. Не меняй правила Play Mode и глобальные настройки инструментов ради установки.
