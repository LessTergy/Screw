# Анализ изменений и локальный коммит

Подготовь один связный коммит с сообщением о фактически выполненных изменениях: что сделано, для чего и каков итог. Сообщение коммита целиком пиши строго на английском языке, включая заголовок, основной текст и названия разделов. Общение и отчёт пользователю веди на русском. Имена файлов, символов и API сохраняй в исходном написании.

В сообщении коммита описывай только выполненные изменения и их назначение. Не добавляй разделы `Verification`, `Testing`, результаты проверок, команды проверки, сведения о недоступных валидаторах или оставшихся ручных проверках. Проверки по-прежнему выполняй по процессу ниже, а их результаты и ограничения сообщай только в отчёте пользователю в чате.

Описывай выполненную работу в утвердительной форме прошедшего времени: `Added`, `Implemented`, `Fixed`, `Updated`, `Documented`. Это относится и к заголовку, и к пунктам об изменениях. Не используй повелительные `Add`, `Implement`, `Fix`, `Update`, `Document`: сообщение должно фиксировать результат, а не звучать как поручение. Для текущего поведения допустимы утверждения вроде `The pool now accepts five bolts`.

История доступного чата объясняет **зачем** выполнялась работа. Текущий Git diff определяет **что именно** попадёт в коммит. Ни планы, ни прежний отчёт AI сами по себе не доказывают наличие реализации или успешной проверки.

## 1. Определи запрос и границы

- Прочитай действующие инструкции репозитория и примени обязательный процесс выполнения задач соразмерно работе. Соблюдай ограничения на CodeGraph, чтение сцен и префабов, Unity MCP и ручную приёмку. Коммит не означает, что непроверенный Gate завершён.
- Вызов skill с поручением оформить изменения включает создание локального коммита. Не запрашивай повторное разрешение на обычный коммит в уже определённом объёме. Если пользователь просит только анализ, черновик сообщения, создание или изменение skill, работай без staging и коммита.
- Установи область: все явно запрошенные изменения, перечисленные пути или результат конкретной задачи из текущего чата. Если область не указана, используй однозначно определяемую законченную задачу. Не приписывай AI авторство каждой изменённой строки и не исключай нужные пользовательские правки только из-за их авторства.
- При нескольких несвязанных наборах изменений уточни состав коммита, если его нельзя надёжно определить из запроса и контекста. По умолчанию готовь один коммит выбранной задачи; не объединяй независимые задачи и не разбивай работу на дополнительные коммиты без основания в запросе.

## 2. Собери фактическое состояние Git

Установи корень репозитория, текущую ветку, наличие `HEAD`, исходное состояние индекса и рабочего дерева. Используй доступные read-only команды, например:

```text
git rev-parse --show-toplevel
git status --short --untracked-files=all
git diff --stat
git diff --cached --stat
git diff --name-status
git diff --cached --name-status
git ls-files --others --exclude-standard
```

- Различай unstaged, staged и untracked. Обычный `git diff` не показывает новые неотслеживаемые файлы: отдельно изучи относящееся к задаче содержимое таких файлов. Удаления и переименования тоже входят в анализ. Для автоматической обработки имён используй NUL-разделители, а не разбиение путей по пробелам.
- Если `HEAD` существует, посмотри несколько последних сообщений через `git log`, чтобы учесть принятую структуру. Язык и повелительная форма прежних коммитов не отменяют требования этого skill к английскому языку и описанию выполненной работы. При отсутствии первого коммита не используй команды, требующие существующего `HEAD`: это допустимый initial commit, а `git diff --cached` работает и без него.
- Если Git-репозитория нет, сообщи об этом; не выполняй `git init` без поручения. При конфликтах или незавершённом merge/rebase/cherry-pick останови обычный сценарий коммита и назови состояние. Не завершай чужую операцию автоматически. При detached HEAD уточни целевую ветку, если пользователь не разрешил коммит в этом состоянии.
- Не редактируй `.gitignore`, настройки Git, исходники, assets и документацию ради подготовки коммита. Не включай случайно секреты, локальные настройки и генерируемые каталоги Unity. При обнаружении существенной проблемы объясни её; не исправляй посторонние файлы в рамках оформления коммита.

## 3. Сопоставь изменения с историей задачи

Прочитай относящиеся к выбранной области diff и необходимые документы. Перед анализом изменённого кода выполни обязательный по `AGENTS.md` запрос CodeGraph: перечень путей из Git не заменяет анализ зависимостей. Если обязательный граф недоступен, останови зависимую работу, не обходи ограничение чтением diff кода. Для изменений только документации и skills граф не требуется.

Из доступного чата извлеки исходную задачу, принятые уточнения, окончательные решения, причины существенных изменений и результаты проверок. Не утверждай, что прочитал другую беседу, если её содержимое недоступно. Нехватка истории не блокирует коммит, когда diff и документы достаточны.

Сопоставляй утверждения с конечным состоянием:

- Описывай итоговую реализацию, а не обсуждавшиеся варианты и промежуточные исправления, уже отсутствующие в diff.
- Составь по diff перечень существенных результатов выбранной задачи, включая документы, планы разработки, skills, настройки и зависимости, а не только код. Для добавленных или существенно изменённых skills установи их имена и назначение; для плана разработки — какие этапы, зависимости и критерии готовности он определяет. Готовый план и skill для составления планов являются разными результатами: наличие второго не подтверждает создание первого.
- Указывай причины из чата, только если они относятся к фактически выбранному изменению. При расхождении выясни итог по файлам; неоднозначность, влияющую на состав коммита, уточни.
- В отчёте пользователю разделяй выполненные проверки, проверки, подтверждённые пользователем, и оставшиеся ручные проверки. Не превращай «нужно проверить» в «проверено». Проверка старого состояния не подтверждает более поздние правки.
- Для бинарных файлов и материалов, чтение которых ограничено инструкциями проекта, опиши только установленный факт добавления/замены/удаления и доступные сведения. Не приписывай им конкретные настройки Inspector, сцен или поведение без подтверждения. Если этого недостаточно для понимания существенного изменения, запроси недостающий контекст.
- Учитывай связанные Unity `.meta` и сохранение GUID при перемещениях; не добавляй утверждение о сохранённых ссылках без основания.

## 4. Выбери и подготовь точный состав

Перед изменением индекса кратко сообщи выбранную область и суть будущего коммита. Это уведомление, а не обязательный запрос подтверждения.

- Сохрани исходные staged-изменения. Если в индексе есть посторонние правки, не включай их и не снимай с staging самостоятельно: сначала согласуй их участие или способ изоляции. Не выполняй обычный коммит всего индекса в надежде, что постороннее останется вне него.
- Если файл частично staged, не заменяй подготовленную версию полным рабочим файлом, кроме случая, когда запрос явно включает и оставшиеся изменения. Для нужной части используй поддерживаемое частичное добавление; если её нельзя уверенно отделить, уточни область, не переписывая рабочее дерево.
- Добавляй только проверенные пути через `git add -- <пути>` с корректным quoting или поддерживаемый pathspec-файл. Не используй `git add .`, глобальный `git add -A`, `git commit -a` и автоматическое включение всех untracked-файлов. Не применяй `--force` к игнорируемым файлам без явного основания.
- После staging заново прочитай **`git diff --cached`** и его список путей. Именно индекс определяет содержание обычного коммита. Проверь соответствие выбранной задаче; выполни `git diff --cached --check` и только необходимые проверки, разрешённые проектом. Замечания форматирования оцени по контексту, не исправляй их молча.
- Если подходящих изменений нет, сообщи об этом и не создавай пустой коммит. Для первого коммита анализируй фактическое содержимое выбранных файлов как initial snapshot, не выдумывая поведение «до».

## 5. Составь подробное сообщение

Короткий английский заголовок называет конкретный выполненный результат в прошедшем времени. Conventional Commits используй, если это принято в проекте или запрошено, сохраняя эту форму после префикса: например, `docs: Added the development plan`. После пустой строки объясни причину и сгруппируй существенные изменения по смыслу. Подробность определяется числом и значимостью результатов, а не только объёмом кода.

- Раскрой каждый существенный результат из перечня, собранного на этапе анализа: что было сделано, для чего и каков итог. Не скрывай самостоятельные результаты за фразами `Updated documentation` или `Added project files`.
- Если в коммит входит план разработки, явно опиши его создание или пересмотр, охват этапов, зависимости и Gate. Если входят skills, назови их и объясни назначение каждого; связанные skills можно объединить в один содержательный пункт. Аналогично отрази существенные изменения требований, конфигурации, assets и зависимостей, если они присутствуют в выбранном составе.
- Перед коммитом сопоставь сообщение со всем staged diff в обе стороны: каждый существенный результат должен быть описан, а каждое утверждение об изменениях — подтверждаться файлами. Не добавляй отсутствующий результат ради полноты и не выдавай описанную в плане реализацию за выполненную.

Пример языка и структуры для коммита, в котором действительно добавлены план и skills:

```text
Added the MVP development plan and project workflow skills

Established an implementation sequence and reusable project workflows
to guide MVP delivery and verification.

Changes:
- Documented development stages, their dependencies, and acceptance gates.
- Added the linear-development-plan skill for dependency-based planning.
- Added the git-commit skill for reviewing changes and creating local commits.
```

Это иллюстрация, не готовое сообщение: состав выполненных изменений всегда устанавливай заново по текущей задаче. Для небольшой задачи достаточно нескольких содержательных абзацев; для нескольких существенных результатов нужен подробный основной текст. Укажи реальную несовместимость, миграцию или ограничение, вызванные изменениями, если они есть. Исключи историю переписки, внутренние рассуждения AI, неподтверждённые заявления, секреты и личные сведения. Все перечисленные изменения должны присутствовать в staged diff; намерения на будущее не выдавай за выполненную работу.

## 6. Сделай и проверь коммит

1. Покажи подготовленное сообщение в кратком обновлении. Если коммит уже поручен и блокеров нет, продолжай без ожидания дополнительного подтверждения.
2. Сохрани точный текст с реальными переносами строк в отдельный временный файл UTF-8 вне рабочего дерева. Используй `git commit --file <путь-к-файлу>` **без списка путей**, чтобы коммитить проверенный индекс. Передача путей в `git commit` меняет его семантику и может включить рабочую версию вместо изученного staged-содержимого.
3. Перед вызовом ещё раз проверь ветку, `HEAD` и выбранные изменения на параллельные правки. Зафиксируй дерево проверенного индекса через `git write-tree`. При неожиданном изменении повтори анализ затронутой части и обнови сообщение; не добавляй новые правки автоматически.
4. Выполни обычный локальный коммит. Не выполняй push, amend, rebase, reset, checkout/restore, stash, clean, смену ветки или настройку автора без отдельного поручения. Не обходи hooks и подпись через `--no-verify`, отключение проверок или изменение конфигурации.
5. При ошибке проверь, был ли коммит создан, и сообщи точную причину. Не повторяй команду вслепую. Если hook изменил файлы, заново изучи diff перед возможным staging и повтором; если требуются новые правки вне запроса, остановись. Отсутствие identity или проблемы подписи не исправляй придуманными значениями.
6. После успеха прочитай фактический новый коммит: hash, родителей, полное сообщение и список изменений; проверь `git status`. Сравни дерево коммита с зафиксированным деревом индекса, а родителя — с исходным `HEAD`. Если hooks или параллельная работа изменили содержимое, сообщи расхождение и не переписывай историю автоматически. Отсутствие первого родителя у initial commit ожидаемо.

В финальном ответе укажи короткий hash, заголовок, основные изменения и существенные результаты проверок. Сообщи, что осталось незакоммиченным; чистоту рабочего дерева утверждай только по последнему `git status`. Если пользователь просил только сообщение, верни полный подготовленный текст и явно укажи, что коммит не создавался. Если коммит заблокирован, дай готовое сообщение, если его удалось достоверно подготовить, и конкретный следующий шаг.
