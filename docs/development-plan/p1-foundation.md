# P1. Экспортные данные и тестовое окружение

[Индекс и статусы](README.md)

## Цель

Проверить исходные связи всех 20 уровней и подготовить минимальный контракт игровых описаний и тестовое окружение.

**Вход:** проект, [правила кампании](../game-design/campaign.md), [аудит уровней](../levels/README.md), исходные prefab/JSON и палитра. Перед выполнением учесть собственный код через CodeGraph; переиспользовать подходящие результаты. Аудит структуры уже доступен, но не заменяет исполняемую валидацию/настройку.

**Границы:** экспорт, контракт и валидаторы; назначение групп реальным болтам и очереди Level_01 готовится после геометрии в P3.7, остальных моделей — в P4C.2. Готовые игровые описания здесь не обещаются. Проверки контракта используют законченные тестовые фикстуры, а не производственные заглушки.

Подготовленные API, свидетельства компиляции/read-only проверки и пошаговая пользовательская часть находятся в [инструкции P1](../levels/foundation.md). Статус и подтверждение Gate обновляются только в индексе, не в этом файле. Постоянный каталог ссылок создаёт пользователь одной командой меню; исходные префабы/JSON при этом не изменяются.

## Задачи по порядку

1. **P1.1.** Подготовить runtime- и тестовые сборки для Edit Mode и Play Mode. Проверка: пользователь подтверждает компиляцию и обнаружение тестов в Test Runner.
2. **P1.2.** Подготовить чтение существующей схемы version 1 и явные ссылки на фактические assets всех 20 уровней/12 вариантов палитры. Сохранять ownerId, boltIds, nodePath, childIndex и порядок allowedBoltPaletteIndices; экспортные пути Assets/UnscrewFirst20 не использовать для загрузки. Определить небольшой контракт игрового описания: ссылка на исходный уровень, цветовые группы с boltId и контейнерные записи; вместимости 3/5 фиксированы. Трансформации и владельцев повторно не хранить. Автотесты чтения охватывают Level_01 и Level_20, неизвестную версию, пустые/повреждённые данные и отсутствие обязательных полей; ошибки явные, исходные файлы не мутируют.
3. **P1.3.** Валидировать все 20 исходников: уникальные номера/ID, существующий единственный владелец, равенство прямых/обратных креплений, разрешимые пути и childIndex, равенство каталога отдельным JSON, назначенные меши/asset-ссылки, уникальные индексы палитры 0…11. Для контракта игровых описаний проверить на фикстурах N=2/5/10 независимость групп/владельцев, полное покрытие болтов без дублей, положительные кратные трём количества по цветам и равную вместимость контейнеров. Некорректные данные отклоняются. Не требовать три болта на деталь или шесть каждого цвета; проверить границы 1 и 11 креплений.
4. **P1.4.** Пользователь проверяет доступность Android Build Support, средств подключения устройства и самого устройства для финальной приёмки.

## Приёмка и Gate

Пользователь запускает Edit Mode тесты P1.2–P1.3, проверяет регистрацию сборок и реальные ссылки assets. Все 20 исходников проходят структурную проверку; повреждённые фикстуры отклоняются. Результат: пригодная геометрическая основа и проверяемый формат будущих игровых описаний. Решаемость, W и работа runtime пока не подтверждаются.

**Gate:** тестовые сборки работают, исходные данные всех 20 моделей и тесты контракта проходят, ссылки назначены пользователем, окружение Android-проверки доступно. Свидетельства: Test Runner и подтверждение пользователя в индексе до P2. Готовность игровых описаний Level_01/02–20 будет отдельным результатом P3/P4C.
