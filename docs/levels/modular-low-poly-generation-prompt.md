# Составные low poly модели и метаданные уровней: анализ и промты-ТЗ

Дата: 06.11.2026. Назначение: подготовка нового контента в стиле приложенных референсов для существующей механики Screw. Этот документ не заменяет действующую кампанию и не поручает изменять её assets.

Для стандартного черновика сначала согласуй референс, затем выполни промт A и оставь модель открытой в Blender для осмотра. После отдельного одобрения модели передай пакет в [локальный импортёр Unity](generated-level-pipeline.md). Импортёр выполняет подготовку из промта B для поддерживаемого формата. Промт B также описывает контракт и приёмку при отдельной подготовке метаданных.

## 1. Как устроены существующие уровни

Анализ выполнен через CodeGraph, исходные JSON, код подготовки/проверки уровней и сохранённые отчёты. Unity Editor в этой задаче не опрашивался. Исторические сведения об иерархии взяты из `docs/levels/README.md` и сопоставлены с текущим контрактом валидации, а не с живым состоянием prefab.

- В каталоге 20 уровней, 692 детали и 1611 болтов. Отдельные `Level_NN.json` совпадают с записями каталога; это дополнительно проверено чтением JSON. В уровне 4–59 деталей и 9–111 болтов, на детали 1–11 креплений. Число деталей и болтов не задаёт монотонную кривую сложности.
- Модель собрана из отдельных игровых модулей. Модуль снимается целиком после извлечения последнего принадлежащего ему болта. Это заранее подготовленное разделение, а не разрезание общей сетки во время игры.
- В конечном представлении детали — непосредственные дети `Assembly/Model`, болты — непосредственные дети `Assembly/Bolts`. Болты не являются дочерними объектами своих деталей.
- Принадлежность задана явно: `bolts[].ownerId → parts[].id`, обратно — `parts[].boltIds`. Положение рядом с поверхностью и имя объекта не заменяют эту связь. У одного болта один владелец, даже когда визуально он расположен у стыка.
- Геометрическое описание, игровая раскладка и маршрут разборки разделены. Цветовая группа может включать крепления нескольких деталей; деталь может удерживаться болтами разных цветов. Тройки относятся к сортировке, а не к количеству болтов на детали.
- Конечная игра использует два активных контейнера по три места и пул на пять. Общее число болтов и число болтов каждого цвета должны быть кратны трём.
- У болта локальная ось от стержня к головке — `+Z`. Выбор требует ближайшего попадания в его коллайдер и обращённости головки к лучу; коллайдеры деталей блокируют болты за ними.
- После освобождения деталь становится динамической и падает под действием гравитации. В исследованном `LevelPartPhysics.ReleaseAsync` экспортный `sourceReleaseForce` не используется для выталкивания детали. Нельзя рассчитывать на него, чтобы извлечь геометрически запертую часть.
- Коллайдеры деталей сохраняются заранее; runtime не анализирует меш. Общий владелец геометрии и коллайдеров — prefab модели, а не отдельные экземпляры в сценах.

### Почему требование к сетке существенно

В сохранённом `Assets/Content/ModelRepairs/rcv_005/Report.json` перечислены 37 проблемных деталей с сообщением об открытых границах или несогласованном winding. В этом отчёте ни одно исправление не отмечено как применённое. Это состояние отчёта, а не повторный аудит нынешних ссылок MeshFilter.

Текущий `PrimitiveColliderBaker.ValidateTopology` проверяет конечность координат, наличие объёма и согласованность рёбер после геометрического сопоставления вершин. Он допускает некоторые коллинеарные стыки и пропускает треугольники, схлопнувшиеся после такого сопоставления. В этом методе нет полной проверки самопересечений, manifold-окрестностей всех вершин и пересечений между деталями. Поэтому «прошёл текущий валидатор» — необходимая проектная проверка, но недостаточное доказательство качества новой модели.

Новая модель должна сразу быть корректным объёмным объектом. Автоматическое залатывание, скрытие изнанки материалом и внешний коллайдер не считаются штатным способом довести поставку до готовности.

Из скриншотов нельзя установить число скрытых частей, реальную топологию, толщины, внутреннее устройство или точную принадлежность каждого болта. Эти характеристики ниже являются требованиями к нашей поставке.

Желаемый стиль: узнаваемая игрушечная фигура, собранная из крупных деталей конструктора, с простыми силуэтами, чистыми цветами и небольшими скруглениями. Low poly здесь означает прежде всего простоту формы и сборки. Сплошная треугольная огранка, мелкая воксельная крошка и механическое уменьшение полигонов у сложной скульптуры не дают нужного результата. Дополнительные LEGO-пупырышки, логотипы и настоящие защёлки не требуются.

## 3. Как использовать промты

Порядок работы: **одобренный референс → промт A → проверенная модель на осмотр в Blender → одобрение модели → импорт и метаданные по промту B → проверка разборки**.

Промт A предназначен для исполнителя с доступом к созданию и экспорту настоящей 3D-геометрии. Сервис, способный выдать только изображение, может подготовить концепт, но не выполнить ТЗ целиком. Промт B требует доступа к результату A, его манифесту и проектным контрактам; одного рендера недостаточно.

Численные художественные бюджеты ниже — предлагаемый стартовый профиль нового контента, а не измеренные ограничения устройства и не параметры текущих моделей. Их можно уточнить до генерации. Требования к целостности сетки, связям ID и честности проверок обязательны.

## Промт A. Генерация составной модели

Ты — 3D technical artist, создающий игровые модели для мобильной пространственной головоломки с выкручиванием болтов. Создай настоящую составную 3D-модель, которую можно последовательно разобрать на отдельные модули. Подготовь исходник, экспорт, манифест и отчёт о проверке. Не ограничивайся картинкой или описанием предполагаемой модели.

### Входные параметры

- Тема и силуэт: `{например: сидящий кот / мороженое на палочке / маленький робот}`.
- Идентификатор модели: `{modelName}`, уникальный и стабильный.
- Профиль: `{intro / standard / advanced}`.
- Целевое число деталей: `{partCount}`.
- Целевое число болтов: `{boltCount}`, положительное, кратное 3, минимум 6 для совместимости с двумя цветами.
- Масштаб: максимальный размер собранной модели без болтов — 14 условных единиц; модульная единица `u = 1`. Это нормализация авторинга, не заявление о физических метрах игрушки.
- Главный референс: `{файл одобренного изображения и выбранный вариант}`. Используй саму картинку при моделировании. [Одобренный будильник C](generated-level-pipeline.md#визуальный-эталон-для-новых-моделей) задаёт уровень сходства и характер игрушечного пластика. Кот, эльф и мороженое остаются примерами крупной модульности.
- Образец общего болта и его реальные размеры: `{предоставленный asset или точная спецификация}`. Если их нет, подготовь только размеченные крепёжные точки и явно отложи проверку посадки болтов; не объявляй сборку готовой для игры.

Если параметры не заданы, предложи один вариант: стандартная модель из 12–20 модулей, преимущественно 1–3 болта на модуль; выбери суммарное кратное трём количество креплений. Согласуй только противоречащие друг другу обязательные параметры. Не добавляй лишние варианты исполнения.

### A1. Художественная форма

1. Сними с одобренной картинки основные пропорции, углы наклона и положение характерных деталей. Построй по ним крупные объёмы. Используй столько сегментов, сколько нужно для сохранения видимого контура. Скрытые стороны дострой по логике формы и укажи допущения при показе.
2. Основные поверхности широкие и спокойные. Модульность должна читаться формой и стыками. Не создавай искусственную сетку швов на монолитной геометрии.
3. Допускаются небольшие фаски: обычно 1–2 сегмента. Для небольших цилиндрических элементов ориентируйся на 8–12 сторон; увеличение оправдывай силуэтом. Не используй subdivision ради гладкости плоских блоков.
4. Сохраняй ощущение цветного пластика: непрозрачные материалы, умеренные блики, без фотореалистичных пор, царапин и шума. Не запекай свет и тени между модулями, которые затем будут сниматься.
5. Основная палитра самой фигуры — ориентировочно 3–6 цветов. Цвета болтов — отдельная игровая палитра; цвет корпуса не определяет их группу. Проверяй различимость головок на фоне детали.
6. Глаза, полосы, нос, декоративные пояса и подобные мелочи по возможности делай материалами на поверхности соответствующего модуля. Если нужна выступающая геометрия, она должна составлять с ним корректное единое тело. Не добавляй самостоятельные физические детали ради мелкого декора.
7. Не делай буквальные замковые соединения конструктора, тугие штифты, взаимно сцепленные кольца и поднутрения, удерживающие освобождённые модули. Требуется визуальная логика конструктора и свободная разборка.
8. Фон, реквизит и элементы интерфейса держи отдельно от игровых мешей. Предметная подставка из одобренного референса может быть игровой деталью.
9. До передачи на осмотр сравни рендер и картинку в близком ракурсе и масштабе. Исправь заметные различия в силуэте, пропорциях и палитре. Если точное повторение конфликтует с разборкой или коллайдерами, покажи конкретный конфликт пользователю до замены формы.

### A2. Разделение на игровые модули

1. Один снимаемый модуль — один отдельный mesh-object с устойчивым именем `Part_000_<Meaning>`, `Part_001_<Meaning>` и т. д. Каждое имя уникально, без `/`. Один модуль снимается как одно твёрдое тело.
2. Внутри модуля должен быть один связный объём материала. Не объединяй в один объект разнесённые острова ради уменьшения числа объектов. Полости разрешены только намеренные и корректно оформленные; отдельная внутренняя оболочка полости не считается самостоятельным островом материала.
3. Каждый модуль имеет ненулевую толщину и полную замкнутую поверхность, включая грани, скрытые в собранном состоянии. После снятия соседей не должны открываться отсутствующие задники.
4. Соседние модули не должны пересекаться объёмами. Предусмотри небольшой различимый зазор; стартовый ориентир 0,02–0,05 `u`, уточняемый по масштабу и посадке болтов. Намеренный контакт разрешён, взаимное проникновение — нет.
5. Не делай огромную скрытую болванку внутри всех частей. Если нужен сердечник, он тоже отдельная снимаемая деталь с собственными креплениями и доступным этапом разборки.
6. Предусмотри внешние, средние и внутренние части там, где это помогает головоломке. Снятие внешнего модуля может открывать новые головки. Не обязательно делать строго вложенные концентрические оболочки.
7. Для вводной модели допустимы 4–8 крупных деталей и почти прямая разборка; для стандартной — 12–24; для сложной — 24–36. Это ориентиры. Не дроби модель, чтобы формально попасть в диапазон.
8. После удаления последнего крепления у каждого модуля должен существовать свободный выход из сборки при допустимом повороте уровня. Укажи его в манифесте. На этапе физической проверки выход должен подтверждаться реальным падением; телепортация и отключение препятствий не допускаются.

### A3. Обязательная корректность сетки

Проверяй каждую деталь отдельно, затем сборку, затем повторно импортированный экспорт.

- Только конечные координаты и корректные индексы. Никаких NaN, Infinity, нулевых рёбер и треугольников нулевой или численно неустойчивой площади.
- Геометрическая поверхность замкнута и является ориентируемым 2-manifold: у каждого геометрического ребра ровно две инцидентные грани, у вершины корректная manifold-окрестность. Нет T-junction, висячих вершин, открытых границ, дублирующих и внутренних паразитных граней.
- Winding согласован. Внешние грани направлены из материала наружу, стенки полостей — из материала в пустоту. Проверяй ориентацию оболочек и объём, а не только отображаемые нормали.
- Нет самопересечений треугольников и пересечений оболочек. Нормальные общие рёбра и вершины соседних граней не считаются самопересечением.
- Отверстие — полноценный замкнутый объём материала вокруг пустого канала: есть внутренняя стенка и корректные переходы. Не путай сквозной канал с незашитой дырой в поверхности.
- Геометрию толщины, фасок и отверстий действительно создай и примени перед экспортом. Не используй двусторонний материал, чтобы скрыть отсутствующие поверхности.
- Жёсткие нормали и UV-швы могут требовать нескольких render-вершин в одной геометрической точке. Проверяй топологию на отдельной геометрической копии с контролируемым допуском сопоставления, сохраняя UV, normals, материалы и швы исходного render mesh. Не склеивай близкие разные поверхности.
- Зафиксируй допуски анализа в единицах модели. Для модели с максимальным размером 14 стартовый допуск геометрического совпадения — порядка `1e-5 u`; он должен быть существенно меньше минимального зазора и толщины. Порог площади задаётся отдельно в квадратных единицах. Укажи фактически использованные значения.
- Не применяй глобальный remesh/decimate ко всей сборке. Если используются boolean или упрощение, выполняй их на отдельной детали, после чего заново проверяй весь результат. Не допускай исчезновения полостей, слияния модулей, изменения крепёжных мест и незапланированных островов.
- Финальный экспорт содержит явные треугольники. В исходнике разрешены quads, но результат триангуляции должен быть заранее зафиксирован и проверен.
- После экспорта заново прочитай файл и проверь те же инварианты. Исправный исходник не доказывает исправность экспорта.

При обнаружении дефекта исправь его до поставки. Если проверка недоступна или ошибка не устранена, назови конкретный модуль и дефект, пометь результат как `failed` либо `not_checked`; не выдавай его за принятую модель.

### A4. Простой бюджет геометрии и коллайдеров

- Стартовая цель: обычно 50–400 треугольников на модуль; до 800 для элемента, определяющего силуэт. Для стандартной фигуры ориентир — до 8 000 треугольников без общего болта, верхний ориентир — 15 000. Это бюджет авторинга; производительность ещё требует измерений в игре.
- Предпочитай один материал на модуль и небольшую переиспользуемую палитру. Дополнительные material slots оправдывай видимыми цветовыми зонами. Не создавай материал на каждый полигон.
- Деталь проектируй так, чтобы её игровую форму можно было приблизить обычно 1–3 примитивами, для отдельных сложных модулей — до 6. Это цель упрощения нового контента, не нынешний лимит baker.
- Разрешены только BoxCollider, SphereCollider, CapsuleCollider. Для автоматической подготовки весь объём каждого примитива должен лежать внутри материала детали. Проверки центра или восьми углов недостаточно для сложной формы: нельзя перекрыть полость между ними.
- Сохраняй важные просветы и блокирующие поверхности. Не сокращай число примитивов ценой перекрытия пустоты. Если бюджет не достигается, сначала упрости модуль; явно сообщи о несоответствии, не добавляй десятки боксов молча.
- Сведения о предлагаемых примитивах можно включить в манифест как данные авторинга. Они не становятся готовыми Unity-компонентами автоматически. Общую физическую настройку при интеграции сохраняй у общего prefab модели.

### A5. Крепёжные точки и разборка

1. Запланируй настоящие позиции и ориентации всех крепёжных точек. Преимущественно 1–3 болта на модуль; четыре допустимы по размеру и композиции. Не требуй тройку на каждой детали.
2. У каждой точки один `boltId` и один `ownerPartId`. Сумма креплений всех деталей должна совпадать с общим числом болтов.
3. Головки находятся снаружи поверхности владельца и не утоплены в его блокирующий объём. Стержень может входить в владельца. Намеренное перекрытие головки другим модулем разрешено лишь при существовании более раннего этапа снятия этого модуля.
4. Направление наружу — локальная `+Z` корня болта. Проверяй поворот во всех ракурсах; нельзя назначить одинаковую rotation точкам на разных сторонах модели.
5. Для общего болта оставь достаточно места под визуальную головку, её область нажатия и извлечение. Не ставь головки вплотную к краю, друг в друга и в узкие щели. Если размеров общего болта нет, не выдумывай подтверждённые расстояния.
6. Для каждого этапа разборки должен быть хотя бы один болт, доступный с допустимого ракурса; после снятия всех болтов владельца открывается следующий этап. Исключи циклическую блокировку и навсегда спрятанные головки.
7. Не выводи доступность из ID, декоративных швов или условного номера слоя. План разборки — гипотеза до геометрической проверки лучами и последующей проверки в игре.

### A6. Координаты, иерархия и экспорт

Целевая система данных игры: Unity, Y-up, левосторонняя система; `+Z` корня болта направлена к головке. GLB имеет собственную правостороннюю систему координат. Явно опиши преобразование систем, единиц, нормалей и ориентаций. Не помечай GLB как левосторонний без преобразования и не делай повторный пересчёт при импорте.

Целевая иерархия игрового представления:

```text
Level_NN
└─ Assembly
   ├─ Model
   │  ├─ Part_000_<Meaning>
   │  ├─ Part_001_<Meaning>
   │  └─ ...
   └─ Bolts
      ├─ Bolt_000_Owner_000
      │  └─ ShowTrans/TurnTrans/Mesh
      └─ ...
```

- В DCC разрешены маркеры корней болтов вместо копирования общего болта. Явно пометь их как маркеры. При последующей интеграции их должны заменить экземпляры существующего общего bolt prefab с нужной внутренней иерархией. Маркер не считается готовым игровым болтом.
- Сохрани имена, порядок детей и локальные трансформации модулей. Если экспортёр меняет порядок, манифест строится по фактическому конечному результату. Не используй случайный порядок обхода для ID.
- Для новой модели предпочитай единичный положительный scale объектов и запечённые размеры мешей. Не допускай отрицательного scale и shear. Повороты/позиции деталей допустимы и сохраняются в файле модели.
- При выборе локального pivot около центра детали не меняй её собранную позу. Общий pivot всех частей также технически возможен, но не нужен специально. После экспорта проверь реконструкцию исходной сборки.
- У нового `Level_NN` — position `[0,0,0]`, rotation `[0,0,0]`, scale `[1,1,1]`. `Assembly` и `Model` по возможности также без дополнительных преобразований: размер уже подготовлен в геометрии. Не копируй исторические масштабы 15 и 1,2 из другого уровня.
- Экспортируй самодостаточный GLB 2.0 с одной непустой сценой и сохрани редактируемый исходник Blender. Для черновика Unity prefab создаёт команда **Tools → Screw → Levels → Import Generated Level**.

### A7. Что выдать

1. Редактируемый исходник модели и финальный экспорт с раздельными модулями.
2. Превью спереди, сзади, сбоку, в ракурсе 3/4 и разнесённый вид. Дополнительно — wireframe и face orientation нескольких характерных деталей, включая внутренние поверхности.
3. `ModelManifest.json` как сопроводительный документ авторинга, не новый runtime-формат игры. Укажи: версию манифеста, modelName, hash финального экспорта, единицы и преобразование осей; для каждого модуля — стабильный ID, имя/путь, локальный transform, bounds, triangle count, material slots, список креплений, предполагаемый выход при разборке; для каждой крепёжной точки — ID, ownerId и фактический transform с указанной системой отсчёта. Схему сопроводительного файла приложи к нему.
4. `MeshValidationReport.json`: инструмент и версия, hash проверенного экспорта, численные допуски, по каждому модулю фактические результаты проверок замкнутости, manifold-рёбер и вершин, winding, вырожденностей, самопересечений, оболочек и объёма. Отдельно — пересечения деталей и соответствие бюджетам. Для каждого пункта статус `passed`, `failed` или `not_checked`; нулевые счётчики ошибок разрешены только после выполненной проверки.
5. Список ещё не подтверждённых условий: посадка общего болта, консервативность коллайдеров, доступность лучами, физическое падение. Не смешивай их со статусом проверки топологии.

Критерий приёмки A: узнаваемая фигура из крупных самостоятельных деталей; проверенная корректная сетка каждого модуля в конечном экспорте; отсутствие взаимных проникновений деталей; сохранённые ID, позы и материалы; пригодность формы к небольшому числу внутренних примитивных коллайдеров. Концепт без геометрии или модель с непроверенными обязательными пунктами остаётся промежуточным результатом.

## Промт B. Метаданные уровня по принятой модели

Ты — technical level designer. На основе принятого результата промта A подготовь данные уровня для существующего проекта Screw. Используй настоящие объекты, трансформации и результаты проверок. Не восстанавливай координаты и владельцев по рендеру, не придумывай данные о доступности и не объявляй уровень решаемым без маршрута.

### B1. Входы и границы

- Финальная модель, `ModelManifest.json` и `MeshValidationReport.json` с совпадающим hash.
- Фактическое конечное дерево узлов и позы после преобразования в целевую систему Unity.
- Общий bolt prefab/спецификация, палитра и параметры камеры.
- Согласованный `{levelNumber}` и `{sourceModelId}`. В текущем коде номер только 1–20, `sourceCampaignIndex = number - 1`, modelId — положительный. Новый уровень нельзя молча записать как 21-й или заменить им существующий слот.
- Контракты `LevelSourceData`, `LevelDataValidator`, `LevelGameplayData`, `LevelRouteData`, `LevelContentCatalogUtility` и `LevelGameplayDefinitionUtility` из текущей версии проекта.

Если доступен только DCC-экспорт без конечного представления и Unity-проверок, выдай подготовительные метаданные и точный список незавершённых проверок. Не выдавай предполагаемые asset paths, viewport points и Editor-прохождения за существующие.

Не создавай новый формат основной геометрии уровня, новый runtime-решатель или генератор уровней для игрока. Применяй существующий контракт. Сопроводительные отчёты не добавляй скрыто в runtime-схему.

### B2. Геометрические метаданные — `Level_NN.json`

Обязательные поля верхнего уровня:

```text
number, sourceCampaignIndex, sourceModelId, sourceName,
modelPosition, modelEulerDegrees, rootEulerDegrees,
modelScale, rootScale, allowedBoltPaletteIndices,
parts, bolts, sourcePrefab, prefab, glb
```

Отдельный файл уровня не содержит `schemaVersion`: в существующем контракте она задаётся каталогом/контекстом чтения. Версия геометрического каталога — 1. Не путай её с версией маршрута 2.

Правила:

- `modelPosition` и `modelEulerDegrees` — локальная поза `Model` относительно `Assembly`; `modelScale` — его единый масштаб.
- `rootEulerDegrees` и `rootScale` в этом контракте описывают `Assembly`, а не внешний корень уровня. Внешний `Level_NN` должен оставаться единичным.
- Для новой модели с уже запечёнными размерами обычно нужны нулевые дополнительные позиции/углы и масштабы 1. Подтверди фактические значения по сборке.
- `allowedBoltPaletteIndices` — упорядоченный список различных индексов существующей палитры 0–11. Длина `N` должна удовлетворять `2 ≤ N ≤ B/3`, где `B` — общее число болтов. Не сортируй список после назначения групп.
- Пути `sourcePrefab`, `prefab`, `glb` указывают на реальные результаты или явно обозначенные ещё не созданные цели в отдельном отчёте. Не копируй исторический `Assets/UnscrewFirst20/...`. Запись с отсутствующими целевыми assets не считается интегрированной.
- Не выдумывай исходный commit, версию Unity или происхождение модели. Служебная идентичность новой модели должна соответствовать фактическому источнику и согласованному локальному ID.

Каждая запись `parts[]` содержит ровно контрактные поля:

```json
{
  "id": 0,
  "childIndex": 0,
  "sourceLayer": 0,
  "boltIds": [0, 1],
  "sourceReleaseForce": [0, 0, 0],
  "sourceSpin": false,
  "name": "Part_000_HeadFront",
  "nodePath": "Assembly/Model/Part_000_HeadFront"
}
```

Это пример формы одной записи, а не готовый уровень. Значения бери из принятой модели. `id` уникален и неотрицателен; `childIndex` — настоящий индекс непосредственного ребёнка `Model`, все индексы образуют перестановку `0…partCount-1`. Путь и имя точно совпадают с конечной иерархией. У каждой детали хотя бы одно крепление. `sourceLayer` — исходная метка, не правило доступности и не индекс Unity physics layer. Для новой модели без исходной метки разрешено явно выбранное значение 0. Нулевой releaseForce и false spin — допустимые нейтральные значения; они не гарантируют падение и не создают специального поведения.

Каждая запись `bolts[]` содержит:

```json
{
  "id": 0,
  "ownerId": 0,
  "position": [0, 0, 0],
  "eulerDegrees": [0, 0, 0],
  "sourceWhitelist": "",
  "nodePath": "Assembly/Bolts/Bolt_000_Owner_000"
}
```

Это пример структуры, нулевую позу нельзя копировать как готовую. `position` и `eulerDegrees` — фактическая локальная поза корня болта относительно `Bolts`, в Unity-координатах и градусах. Не подставляй сюда мировую позу, позу относительно владельца или исходные Euler DCC без преобразования. Преобразование поворотов делай через корректную ориентацию/матрицу, затем сериализуй целевые Euler; не ограничивайся сменой знака одного угла. После восстановления сверяй ориентации, а не равенство неоднозначных Euler-троек.

`sourceWhitelist` сохраняется как служебная строка, для новой модели без исходного значения — пустая. Не используй её как вымышленный список зависимостей. У каждого болта существующий владелец; он встречается ровно один раз в `parts[].boltIds`, именно у этого владельца. Декоративные болты без владельца не добавляй.

Трансформации отдельных деталей хранятся в модели/prefab. Текущая запись `parts[]` их не дублирует и не позволяет восстановить модель из одного JSON. Поставляй геометрию и метаданные вместе.

### B3. Полный геометрический маршрут W

1. Построй последовательность всех boltId, каждый ровно один раз. Не принимай сортировку ID за доказательство доступности.
2. На каждом шаге найди допустимый поворот всей сборки и точку на головке. С учётом ранее снятых объектов ближайшее попадание луча должно приходиться в нужный bolt collider, а головка — быть обращённой к лучу. Проверяй настоящие блокирующие коллайдеры деталей.
3. В геометрическом маршруте скрывай владельца только после снятия всех его креплений. Не удаляй его раньше ради открытия следующего болта.
4. Для текущего формата используй `schemaVersion: 2`, номер уровня, камеру с FOV/aspect и шаги `boltId`, `levelEulerDegrees`, `viewportPoint`. Вращается сборка, а не камера; углы шага — `[pitch, yaw, 0]` относительно исходной ориентации игровой обёртки. Не задавай произвольный roll. Текущий профиль проверки — FOV 60°, aspect 9/16; кадрирование должно соответствовать используемой игровой камере.
5. `viewportPoint` — нормализованные координаты `[x,y]` в пределах `[0,1]`, X слева направо, Y снизу вверх. Вычисляй их проекцией фактической головки после поворота. Не используй координаты картинки или центр экрана для всех шагов.
6. Повтори W через тот же механизм выбора, который использует игра. Отдельно проверь физическую последовательность: снятая деталь должна действительно освободить область и удалиться по игровым правилам, включая допустимые повороты для схода с опоры. Скрытие части в геометрическом стенде не доказывает физического выхода.
7. Если Editor недоступен, маршрут можно пометить только как кандидат. Не выдавай заполненные по предположению точки за проверенное свидетельство.

Схема файла маршрута:

```text
schemaVersion: 2
levelNumber: согласованный номер
camera:
  fieldOfViewDegrees: 60
  aspect: 0.5625
steps: по одному объекту на каждый болт
  - boltId: фактический ID
    levelEulerDegrees: [pitch, yaw, 0]
    viewportPoint: [projectedX, projectedY]
```

Это схема, а не JSON для импорта; финальный файл должен содержать только реальные численные значения и полный список шагов.

### B4. Цветовые группы и контейнеры

Используй существующее правило подготовки после получения W. Пусть `P = allowedBoltPaletteIndices`, `N = P.length`, `B = W.length`, `K = B/3`.

Для болта в позиции `j` маршрута, начиная с 0:

```text
groupId = floor(j / 3) % N
paletteIndex = P[groupId]
```

Объедини все болты одинаковой группы в один `ColorGroupData`. Для контейнеров `k = 0…K-1`:

```text
ContainerGroups[k] = k % N
```

Первые два контейнера активны, остальные образуют общую очередь. Не меняй её по действиям игрока. Группы не соответствуют владельцам; один цвет может возвращаться в нескольких контейнерах.

Подготовь представление данных существующего `LevelGameplayData`: `LevelNumber`, `ColorGroups` с `Id` и `BoltIds`, `ContainerGroups`. Эти имена — поля C#-контракта. В проекте результат хранится в `LevelGameplayDefinition` asset; сопроводительный JSON с этими полями не становится asset автоматически и требует этапа интеграции.

Пример только логики: для W `[0,1,2,3,4,5,6,7,8]` и P `[1,2]` получаются:

```json
{
  "LevelNumber": 1,
  "ColorGroups": [
    { "Id": 0, "BoltIds": [0, 1, 2, 6, 7, 8] },
    { "Id": 1, "BoltIds": [3, 4, 5] }
  ],
  "ContainerGroups": [0, 1, 0]
}
```

Это шесть жёлтых и три синих болта для текущей палитры. Пример не утверждает пространственную доступность произвольной новой модели.

Проверь, что каждая группа положительна и кратна 3, каждый болт назначен ровно одной группе, число контейнеров K, вместимость по каждому цвету совпадает с его числом болтов. Симуляция полного W должна завершить сбор без переполнения. Это конструктивно подтверждает логический победный путь, но ещё не интересность уровня и не безопасность любых действий игрока. Для вводного уровня не требуется искусственно создавать поражение; для более сложного отдельно опиши проверенные варианты выбора и обращения к пулу, не меняя базовую формулу без отдельного задания.

### B6. Критерии готовности

- Все обязательные поля присутствуют, включая нулевые/false значения; нет повторных JSON-ключей, неизвестных ссылок и нечисловых координат.
