## Иерархия и принадлежность

```text
Level_NN                              regular prefab, root Transform
└─ Assembly                           общая трансформация модели и болтов
   ├─ Model                           nested prefab исходной модели
   │  ├─ <part 0>                     Transform + MeshFilter + MeshRenderer
   │  ├─ <part 1>
   │  └─ ...
   └─ Bolts                           контейнер размещённых болтов
      ├─ Bolt_000_Owner_###
      │  └─ ShowTrans
      │     └─ TurnTrans
      │        └─ Mesh                MeshFilter + MeshRenderer
      └─ ...
```

На момент проверки все объекты активны. У каждого уровня одна `Assembly`, одна `Model` и одна `Bolts`. Каждая деталь является непосредственным ребёнком `Model`, без дочерней игровой иерархии; каждый болт — непосредственный ребёнок `Bolts`, отдельный nested instance общего `Bolt_07.prefab`.

**Болты не являются детьми удерживаемой детали.** Связь задаётся JSON: `bolts[].ownerId → parts[].id`, обратная связь — `parts[].boltIds`. Имена `Bolt_012_Owner_005` помогают диагностике, но не заменяют явную связь. Нельзя вычислять владельца по ближайшей поверхности, индексу болта, группе из трёх или родителю Transform.

У Level_01 имена деталей `P00_...` … `P03_...`; у остальных — `Owner_###_<originalName>`, включая китайские символы. Истинное сопоставление: `id`, `childIndex` и `nodePath` из данных. Проверка подтвердила, что пути существуют, имя соответствует записи, а childIndex указывает на ту же деталь. Перестановка/переименование детей требует синхронного обновления данных; предпочтительно сохранять исходную структуру.

## Две независимые группировки болтов

По уточнению пользователя от 29.10.2026:

- **Цветовая группа** — все болты одного цвета на всех деталях одного уровня. Она может содержать 3, 6, 9 и более болтов; повторное использование цвета не создаёт новую цветовую группу.
- **Группа детали** — все болты, прикреплённые к одному модулю. В экспорте она уже задана через `ownerId` и `parts[].boltIds` и может включать болты разных цветов.

У каждого болта ровно один владелец и одна цветовая группа. Сортировка использует цветовую группу, освобождение детали — только группу детали. Количество болтов цветовой группы должно быть кратно трём для полного сбора контейнерами; количество креплений детали такого ограничения не имеет.

Цвета назначаются объектам в runtime из **упорядоченного `allowedBoltPaletteIndices` текущего уровня**, по кругу и без случайности. Тройки при подготовке раскладки — только способ обеспечить баланс контейнеров, а не определение группы. Повтор цикла пополняет уже существующую цветовую группу. Экспорт не содержит готового распределения болтов по таким группам; контракт подготовки описан в [правилах кампании](../game-design/campaign.md).

## Достаточность исходных метаданных

| Вопрос | Что уже есть | Что ещё требуется |
| --- | --- | --- |
| К какой детали относится болт? | `bolts[].ownerId → parts[].id`, обратный список `parts[].boltIds`, пути узлов | Runtime-привязка к этим данным; новую принадлежность придумывать не нужно |
| Какие цвета доступны уровню? | Упорядоченный `allowedBoltPaletteIndices` | Использовать этот порядок без случайности по решению пользователя |
| Как выглядит цвет? | `catalog.boltPalette[index]`: primary/secondary, sRGB и вариант prefab; актуальные материалы в Bolts/Materials | Явные ссылки на текущие assets вместо старых экспортных путей и применение обоих material-слотов в runtime |
| Какой цвет у конкретного болта и какая у него цветовая группа? | В экспорте такого поля/соответствия нет; все болты белые | Отдельное игровое описание с составом цветовых групп, затем отображение группы в индекс палитры |
| Какие контейнеры активны и в каком порядке сменяются? | В экспорте не заданы | Контейнерные записи, согласованные с группами и количеством болтов |
| Доступна ли вся разборка и работает ли физика? | Геометрия/позы и данные владельцев | Проверочные маршруты, коллайдеры, физические компоненты, интеграционная и ручная проверка |

Циклический список цветов сам по себе не определяет, какие boltId входят в цветовую группу. Предложенный в плане способ подготовки через маршрут W заполняет этот пробел; готового распределения в исходниках пока нет. Количества 6 yellow/3 blue для Level_01 — результат этого способа подготовки, а не извлечённая исходная раскладка.

Полученного контекста достаточно для реализации чтения данных, привязок, отдельного игрового описания и проверок. Полностью готовых метаданных головоломки и доказательства решаемости каждой модели экспорт не содержит. Их подготовка предусмотрена P1.2, P3.6–P3.7 и P4C.1–P4C.2, а не требует неизвестной внешней поставки.

Исходные prefab/JSON, меши и материалы без чёткого поручения пользователя не изменять. Игровые описания хранить отдельно; компоненты/коллайдеры готовить на экземплярах или в отдельном представлении. Необходимые правки исходных assets сначала документировать в плане с причиной и проверкой. Текущий анализ таких правок не выполнял.

## Трансформации, pivot и анимация

Внешний `Level_NN` имеет нулевые позицию/поворот и единичный масштаб. Позиция Assembly и Model нулевая. Масштабы **уже применены в иерархии**: например, Level_01 имеет Assembly=1.2, поворот Assembly X=5°, Model=15. У Level_02–20 Model имеет собственный масштаб примерно 0.4232…3.5, а Assembly иногда дополнительный масштаб. Повторное умножение значениями JSON испортит совмещение болтов и геометрии.

Для смены положения/масштаба всей фигуры менять внешнего владельца целого уровня, сохраняя относительное положение Model и Bolts. Масштабировать только Model нельзя: болты находятся в соседней ветке.

У Level_02–20 локальные трансформации деталей — позиция/поворот 0, масштаб 1: размещение запечено в вершинах их отдельных мешей. Значит, `part.transform.position` обычно совпадает с общим pivot модели и **не является центром детали**. Камеру/подсказки/физическое представление нельзя привязывать к этому pivot без учёта геометрических bounds. У Level_01 детали имеют отдельные локальные смещения.

Общий болт:

| Узел | Локальная трансформация |
| --- | --- |
| Bolt_07 | Позиция/поворот 0, scale=1 |
| ShowTrans | Позиция/поворот 0, scale=1 |
| TurnTrans | Позиция/поворот 0, scale=12 |
| Mesh | Position Z=−0.021, Rotation X=90°, scale=1 |

Меш `Bolts/Meshes/Screw004.asset` имеет два submesh и два материала. Геометрия стержня идёт по локальной Y исходного меша; поворот Mesh X=90° переводит её в **локальную +Z болта**. Более широкая головка находится на положительном конце этой оси (подтверждено распределением вершин). Для выкручивания/проверки обращённости нужно учитывать локальную ось болта (`forward`), а не мировую Y и не `up`. `ShowTrans` и `TurnTrans` предоставляют удобные точки управления отображением/вращением, но скриптов анимации в них нет.

Размер головки, коллайдер выбора и параметры анимации ещё нужно проверить на реальной модели. Существующие pivot/масштабы сохранять; при переносе в UI или физическое представление сохранять корректную мировую позу и масштаб.

Все материалы болтов используют `Universal Render Pipeline/Lit`. При смене цвета согласованно обновлять оба слота; нельзя изменять общий material asset ради одного болта. Индекс палитры нулевой, цифра в имени материала начинается с единицы.

Списки `allowedBoltPaletteIndices` различаются по уровням: у Level_01 только [1, 2], у последующих 5–10 значений. Это заменяет три фиксированных R/B/G старого GDD: по решению пользователя наша кампания использует список каждого уровня по кругу, без случайности. Генератор оригинала не исследован; принятое нами правило не выдаётся за его воспроизведение.

В поставке отсутствуют:

- Назначенный игровой цвет каждого болта и баланс количества по цветам.
- Начальные активные контейнеры и упорядоченная очередь.
- Доказанный доступный порядок снятия, победные/ошибочные маршруты.
- Коллайдеры выбора/перекрытия и физические тела деталей.
- Камера, площадка, UI, звуки, сохранения и логика переходов кампании.

## Что означает «уровень работает» в нашем проекте

Ниже — контракт из [GDD §3](../game-design/mvp.md), а не поведение, уже исполненное этими префабами:

1. Создать независимый экземпляр геометрии и состояние попытки с явными связями деталь ↔ болты, цветами и очередью.
2. Камера осматривает всю фигуру; ближайшая поверхность и обращённость головки определяют допустимость выбора. Метаданные sourceLayer/ownerId сами не задают доступность.
3. До снятия назначить место в левом подходящем контейнере либо в пуле. При переполнении болт остаётся закреплённым.
4. После выхода болта из крепления однократно уменьшить счётчик только его владельца.
5. При нуле креплений освободить только эту деталь; остальные остаются неподвижными. Падение не должно сдвигать закреплённую конструкцию. Деталь удаляется через секунду.
6. Завершить перелёты, смены контейнеров и переносы пула; только после этого и удаления падающей детали разрешить следующий ход.
7. Завершить попытку по правилам победы/поражения. Перезапуск отменяет старые операции и восстанавливает тот же уровень; переход кампании использует отдельный следующий номер.

Количество болтов на модуль не связано с вместимостью контейнера. Деталь с 11 болтами не должна падать после третьего снятия. Геометрическое перекрытие может исчезнуть при освобождении соседней детали, но не переносит на неё чужие крепления.

Для неплоских и полых моделей нельзя считать один общий bounding box или произвольную convex-оболочку точным препятствием: они могут закрывать настоящие отверстия и головки. Коллайдеры для выбора и падения должны сохранять нужную доступность; конкретная конфигурация и её работа ещё не проверены. Физическую траекторию оригинала экспорт не гарантирует.

## Что подтверждено и что проверять дальше

Подтверждено read-only анализом Unity MCP:

- Все 20 иерархий перечислены полностью, 692 детали и 1611 болтов, все объекты активны.
- ID уникальны внутри уровня, каждый owner существует, списки boltIds и ownerId согласованы, у каждой детали есть крепления.
- Все nodePath разрешаются; childIndex/name соответствуют деталям.
- Все меши деталей назначены; все болты используют общий белый prefab с двумя материалами.
- Каталог равен отдельным JSON, суммы совпадают, масштабы Assembly/Model согласованы.
- Максимальные отклонения локальной позиции и quaternion-поворота болтов от JSON — 0 во всех уровнях.

Не подтверждено: визуальная видимость и размер головок, полная достижимость с ограничениями камеры, будущие цветовые раскладки/очереди, решаемость, физика, отмена попытки, переходы, производительность Android. Чтение ассетов не является компиляцией игры или прохождением.

Ручная приёмка после появления игровых компонентов:

1. Открыть Level_01 в Prefab Mode, проверить четыре детали и девять болтов; не переименовывать и не перепривязывать узлы без обновления данных.
2. В тестовой сцене назначить ссылки по инструкции реализующего этапа; осмотреть переднюю/заднюю стороны и пределы камеры, убедиться в отсутствии клика сквозь детали и UI.
3. На каждой модели снять крепления одной детали по одному: до последнего она неподвижна, после последнего падает только владелец; перенос болта в пул тоже освобождает крепление.
4. Проверить все 20 назначенных победных маршрутов, переполнение/спасение на подходящем уровне и повтор во время каждой фазы хода.
5. После реализации кампании проверить переход 01→02, промежуточный переход и завершение 20; состояния, объекты и callbacks предыдущего уровня не переносятся дальше.
6. На Android проверить кадрирование, касания, доступность головок, звук и стабильность на крупных уровнях 04/15/20.

Ни один Gate разработки этим аудитом не закрыт. Статусы будущей реализации ведутся только в [индексе плана](../development-plan/README.md).
