# Кампания из готовых уровней

Дата: 29.10.2026. Дополнение к [MVP от 28.10.2026](mvp.md), основанное на анализе [поставленных уровней](../levels/README.md) и ответах пользователя в чате «Обновить план разработки уровней».

## Объём и приоритет требований

Вместо авторского домика A–F на 18 болтов используем **все 20 готовых Level_01–Level_20 как последовательную кампанию**. Не строим новые модели вместо поставленных. При расхождении с GDD это дополнение заменяет только состав контента, цветовую раскладку/очередь и переходы между уровнями. Правила хода, двух контейнеров по три, пула на пять, доступности, падения, победы/поражения, отмены и управления из GDD §2–3 сохраняются.

GDD §4 с домиком остаётся историческим примером. По последующему согласованию с пользователем регрессия P2.6 проверяет общие правила без обязательного воспроизведения домика или его маршрута. Его A→B/C→D, три болта на деталь, R/B/G и последовательности G4/B5 не являются условиями приёмки новой кампании. Список исключений GDD §5 изменён в части дополнительных уровней; сохранения, бустеры, монетизация, runtime-генератор, редактор уровней для игрока и магазинная публикация по-прежнему не входят.

В этой задаче изменяется документация и план. Код, префабы, исходные JSON и настройки не реализуются и не изменяются; все Gate разработки остаются открытыми.

Исходные уровни сохраняются и при дальнейшем выполнении плана. Новые игровые описания и runtime-компоненты добавляются отдельно. Если потребуется правка исходного prefab, JSON, меша или материала, её путь/причина/проверка сначала фиксируются в плане, а изменение выполняется только по чёткому поручению пользователя.

## Подтверждённые решения пользователя

1. Кампания состоит из всех 20 уровней в порядке их номеров.
2. Цветовая группа — **все болты одного цвета в пределах уровня**, независимо от деталей. Это не тройка болтов.
3. Группа детали — все её крепления. Она задаётся владельцем и не обязана совпадать с цветовой группой.
4. Цвета берутся из `allowedBoltPaletteIndices` соответствующего уровня, **по кругу, без случайности**. Список не сортируется и не заменяется первыми N цветами общей палитры.
5. Материалы/цвета назначаются игровым объектам в runtime; белые экспортные префабы не становятся заранее раскрашенными моделями.

## Контракт цветовых групп и контейнеров

У болта независимы `ownerId` и принадлежность цветовой группе. Членство фиксировано для уровня и не меняется при повороте камеры, снятии соседнего болта, заполнении контейнера или перезапуске. ID болта уникален внутри уровня; между уровнями его различают вместе с номером уровня.

Пусть P — упорядоченный список `allowedBoltPaletteIndices`, N — его длина, B — число болтов, K=B/3. В текущей поставке N=2…10, B кратно трём, K≥N, индексы P различны и лежат в 0…11. Эти условия необходимо валидировать, а не считать гарантированными для повреждённых данных.

Для каждого используемого элемента P существует одна цветовая группа g, 0≤g<N. Ей соответствует индекс палитры P[g]; разные группы внутри уровня не отображаются в один цвет. В цветовой группе может быть несколько контейнерных троек. Количество болтов каждой группы положительно и кратно трём; суммарная вместимость предназначенных ей контейнеров точно равна этому количеству.

**Решение подготовки контента в плане:** сначала зафиксировать геометрически допустимый полный маршрут W — упорядоченный список всех boltId с контрольными положениями камеры. Затем для позиции j в W, начиная с нуля, назначить группу `g = floor(j / 3) % N`. Таким образом, очередная тройка маршрута получает следующий цвет списка; после конца списка цикл начинается снова. Все тройки одного цвета объединяются в одну цветовую группу. Тройки не становятся отдельной игровой сущностью и не связываются с владельцем детали.

Это конкретный способ подготовить ещё отсутствующие раскладки, а не установленный алгоритм исходной игры. Порядок W определяется доступностью геометрии; сортировка экспортных ID или sourceLayer не заменяет проверенный маршрут.

Контейнерные записи для k=0…K−1 имеют группу `k % N`. Первые две записи становятся левым и правым активными контейнерами, оставшиеся — фиксированной общей очередью. Ровно K контейнеров по три места обеспечивают вместимость B. Во время игры очередь работает по GDD: левый подходящий контейнер, замена слева направо, перенос из пула до устойчивого состояния. Она не подстраивается под решения игрока.

При прохождении W каждая тройка завершается в соответствующем контейнере, а пул не требуется. Это конструктивная логическая проверка существования победного маршрута; она не доказывает доступность W в 3D, интересность головоломки или наличие ветки поражения. Геометрия и логика проверяются раздельно, затем совместно. Для всей кампании дополнительно нужен хотя бы один подтверждённый игровой сценарий переполнения и спасения при 5/5.

**Пример Level_01:** B=9, P=[1,2] — yellow/blue. Группы получают 6 жёлтых и 3 синих болта. Первые два контейнера жёлтый/синий, очередь — один жёлтый. Жёлтые болты из первой и третьей тройки — одна цветовая группа. С двумя доступными цветами это вводный уровень: не требуется искусственно создавать в нём поражение или предупреждение 5/5.

## Данные и ответственность

| Результат | Ответственность |
| --- | --- |
| Исходные Level_NN.json и prefab | Готовая геометрия, владельцы, пути, масштабы и список палитры; сохраняются как исходный контент |
| Игровое описание уровня | Явные ссылки на текущий prefab/JSON, состав цветовых групп и контейнерные записи; не дублирует трансформации и владельцев |
| Проверочный маршрут W | Контентное свидетельство: порядок boltId и положения камеры; хранится для тестов/приёмки отдельно от runtime-логики ходов |
| Подготовка описания | Разработчик готовит W и согласованное игровое описание по правилу выше; пользователь подтверждает геометрию и результаты Unity-тестов |
| Runtime-инициализация | Создаёт независимую попытку, назначает каждому болту материалы P[g] и окрашивает активные контейнеры по их группам |
| Группа детали | Считает оставшиеся крепления по ownerId; не использует цвет для определения освобождения |
| Цветовая группа | Определяет маршрутизацию в контейнеры; не определяет владельца/геометрическую доступность |

Не нужен runtime-решатель или генератор. Производственная игра получает подготовленное описание и не ищет W при запуске. Подготовку и валидацию конечного набора данных можно автоматизировать обычным тестовым/редакторским кодом без нового пользовательского редактора и дополнительных пакетов. Игровые описания и W ещё предстоит создать в соответствующих этапах; экспорт не выдаётся за эти результаты.

Оба material-слота болта соответствуют одной палитре. Нельзя изменять общий material asset ради одного болта. Нельзя использовать старые строки `Assets/UnscrewFirst20/...` как реальные ссылки или повторно применять уже сохранённые масштабы. Привязки исходных узлов сохраняются; детали с общим pivot не центрируются через Transform.position без учёта геометрии.

## Переходы кампании

Следующие локальные решения сохраняют исключение сохранений из исходного GDD и дают законченный сценарий кампании:

- Новый запуск игры начинает Level_01. Прогресс существует в текущем сеансе; между запусками не сохраняется.
- «Заново» в игре и «Повторить» после результата восстанавливают **текущий** уровень, его группы, очередь и стартовую камеру.
- После победы на Level_01–19 доступна кнопка «Далее». Она начинает только следующий номер; автоматического пропуска, выбора любого уровня или продвижения после поражения нет.
- После победы на Level_20 показывается «Кампания пройдена», следующего уровня нет. «Повторить» перезапускает Level_20.
- Во время перехода кнопки повторного перехода/повтора заблокированы, команды не накапливаются. Сначала отменяются операции старой попытки и удаляются её объекты, затем активируется новый уровень и его ввод.
- Недействительный «Далее», в том числе двойное нажатие и команда после последнего уровня, не меняет номер и не создаёт второй экземпляр. Ошибки конфигурации выявляются валидацией до игры и сообщаются явно, а не обходятся пропуском уровня.

## Проверяемые инварианты

1. Каждый из B болтов встречается ровно один раз в данных владельцев, ровно один раз в цветовых группах и ровно один раз в W.
2. Группы покрывают те же boltId; неизвестные/повторные ID и отсутствующие ссылки отклоняются явно.
3. P, группы, W и контейнерные записи согласованы с формулой; цветовых групп N, суммарно K контейнеров, вместимость по каждому цвету равна числу его болтов.
4. Runtime назначает материал из P, сохраняя оба слота; экспортные assets не мутируют. Повтор даёт ту же раскладку.
5. На детали может быть 1…11 болтов разных цветов. Только снятие её последнего крепления освобождает её.
6. Ход, переполнение, пул, победа и отмена соблюдают GDD §3 при любом числе групп, а не только при трёх цветах старого примера.
7. Смена уровня не переносит болты, заполнение, очередь, физические тела или callbacks старой попытки; повтор не продвигает кампанию.

## Свидетельства готовности

При пересмотре плана выполнен независимый расчёт формулы для фактических B и P всех 20 уровней. Во всех случаях число цветов/контейнеров допустимо, каждая группа имеет положительное кратное трём количество болтов, абстрактный маршрут по тройкам собирает все болты в ровно K контейнеров, в конце активные места и очередь пусты. Суммарно учтено 1611 болтов; для Level_01 подтверждены 6 yellow/3 blue. Расчёт проверяет только позиции в абстрактном W: конкретные пространственные маршруты ещё не подготовлены, материализация runtime и прохождение этим не подтверждены.

Текущий [аудит Unity MCP](../levels/inspection-2026-10-29.json) подтверждает только структуру экспорта. В нём нет игровых описаний, W, прохождений или работающих переходов. Проверки каждой механики, первого законченного уровня, оставшихся 19 уровней, UI и всей кампании запланированы в [development-plan](../development-plan/README.md); запуск Unity-тестов и ручную приёмку выполняет пользователь.
