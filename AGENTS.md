# AGENTS.md

Инструкции для AI-агентов, работающих с проектом `Arcanoid`.

## Язык и коммуникация

- Основной язык общения с пользователем: русский.
- Объяснения, отчеты о работе и вопросы пользователю пиши на русском.
- Имена классов, методов, полей, файлов, namespace и публичных API оставляй на английском.
- Комментарии в коде добавляй только при реальной необходимости. Если комментарий нужен, пиши его на английском.
- Не добавляй комментарии, которые пересказывают очевидное поведение кода.

## Область проекта

- Основной код проекта находится в `Assets/Content/Scripts`.
- Сторонний код в `Assets/3rd-Party` не изменяй без явной необходимости.
- Unity-generated и временные директории (`Library`, `Temp`, `obj`, `Builds`, `Logs`) не редактируй вручную.

## Выполнение задач

- Перед началом каждой новой задачи по проекту прочитай и примени локальный skill [task-execution](.agents/skills/task-execution/SKILL.md) соразмерно масштабу работы. Для запроса только на анализ или ответ выполняй соответствующие этапы без правок.

## Ponytail и экономия контекста

- При реализации и ревью применяй Ponytail; по умолчанию уровень full, если пользователь не выбрал другой уровень или не отключил его. Выбирай самое простое полное решение с учётом общей сложности, стоимости выполнения и сопровождения. Экономия строк или токенов не оправдывает дублирование, дорогую реализацию, пропуск требований и проверок. Инструкции пользователя и проекта имеют приоритет над рекомендациями skill.
- Перед существенной реализацией кратко обозначь владельца изменения и самое простое подходящее существующее или платформенное решение. Новый логический слой, генератор или копирование настройки по экземплярам должны иметь конкретную необходимость в текущей задаче. Сначала проверь возможность одной общей правки.
- Caveman отключён по решению пользователя. Не используй его сжатие, прокси, хуки или инструкции и не включай их повторно без прямого поручения. Для экономии применяй Ponytail и ограничивай запросы нужными файлами, символами, полями и страницами.
- Обрезанный вывод не считай полным: отсутствие записи в нём не доказывает отсутствие файла, зависимости, ошибки или теста. Если скрытые детали нужны для решения, повтори узкий запрос к тому же источнику. Перед точной правкой кода получи полный затрагиваемый фрагмент. Требования анализа через CodeGraph при этом сохраняются.
- В отчёте различай ошибку выбранного решения, сбой инструмента и недостающие данные. Не объясняй усложнение кода сжатием вывода без подтверждения и не заявляй экономию токенов или ускорение без подходящих измерений.

## Анализ кода через MCP CodeGraph

- Перед выводами, рекомендациями, планированием, ревью или изменением кода проекта сначала выполни релевантный запрос к CodeGraph. Для каждого нового вопроса о коде делай отдельный запрос.
- Определи через CodeGraph затрагиваемые файлы и символы, входящие и исходящие зависимости, цепочки вызовов и область влияния. После этого используй чтение файлов и другие инструменты для уточнения деталей.
- Если CodeGraph недоступен, существующий затрагиваемый код не проиндексирован или граф не позволяет оценить его зависимости, не подменяй анализ поиском по тексту и останови задачу по этому коду. Сообщи пользователю, что требуется восстановить доступ или индекс. Если граф подтверждает отсутствие собственного кода, это не препятствует созданию первых скриптов.
- Вопросы о настройке инструментов, документации и файлах без анализа кода не требуют CodeGraph. Отсутствие собственных скриптов на этапе инициализации проекта не блокирует такую работу.

## Уточнение требований

- После изучения доступного контекста проверь, остались ли неизвестные требования, от которых существенно зависят поведение, архитектура, публичные контракты, формат данных, интеграции или критерии готовности.
- Если без ответа возможны несовместимые реализации, собери критичные вопросы в один короткий список и уточни их до окончательного плана и правок. После ответа проверь требования повторно.
- Некритичные детали решай разумным допущением и явно обозначай его, когда оно влияет на результат.

## Документация через MCP Context7

- Для работы с новым или зависящим от версии Unity API, пакетом, SDK или библиотекой получи актуальную документацию через Context7. Для задач по существующему коду сначала определи задействованные символы и зависимости через CodeGraph.
- Проверяй источник найденной документации: если Context7 не возвращает официальный первоисточник, уточни сведения по официальной документации или явно обозначь ограничение.
- Если необходимая для корректного решения документация недоступна, сообщи об этом пользователю и не продолжай методом проб и ошибок.

## Общие принципы кода

- Применяй KISS, DRY и YAGNI; следуй SOLID там, где это действительно улучшает структуру.
- Предпочитай простой, читаемый код, самодокументируемые имена и небольшие методы. Не добавляй абстракции на будущее и не усложняй решение ради паттерна.
- Если требуемое изменение можно корректно выполнить в одном общем месте вместо нескольких, строго выбирай одно место. Сначала найди владельца поведения или настройки: существующий метод, тип, общий asset или базовый prefab. Не копируй одну настройку по экземплярам, сценам или prefab-вариантам, когда её можно наследовать или переиспользовать из общего источника. Учитывай всех потребителей и сохраняй требуемое поведение.

## Коллайдеры 2D и 3D

- Всегда используй примитивные коллайдеры. Для 3D — BoxCollider, SphereCollider и CapsuleCollider; для 2D — BoxCollider2D, CircleCollider2D и CapsuleCollider2D.
- Для сложной формы используй минимальный достаточный составной набор примитивов. Не применяй MeshCollider, PolygonCollider2D и генерацию коллайдеров по полигональной геометрии как способ точного повторения render mesh.
- Проверяй форму и стоимость решения: область взаимодействия, края, промахи, необходимые просветы и блокирующие поверхности. Точность визуального меша сама по себе не является основанием усложнять коллайдеры.
- Общую форму и параметры коллайдера настраивай у общего владельца, предпочтительно в базовом prefab, чтобы все подходящие экземпляры наследовали одну настройку.

## C# и Unity кодстайл

- Всегда используй фигурные скобки для `if`, `else`, `for`, `foreach`, `while`, `do`, `using`, `lock` и других блочных конструкций, включая однострочные.

- Однострочные методы и свойства тоже оформляй с фигурными скобками, если это обычный метод или блоковая логика.
- Expression-bodied members используй только когда это уже соответствует локальному стилю файла и не ухудшает читаемость.
- Для локальных переменных по умолчанию используй `var` вместо явного объявления типа. Явный тип оставляй только когда `var` невозможен или заметно ухудшает читаемость.
- Приватные поля предпочитай именовать в стиле `_camelCase`, если файл не использует другой устойчивый локальный стиль.
- Сериализуемые приватные поля оформляй как `[SerializeField] private ...`.
- Публичные поля в `MonoBehaviour` и `ScriptableObject` не добавляй без необходимости; предпочитай `[SerializeField] private` плюс публичное read-only свойство, если нужен доступ извне.
- Сохраняй существующие namespace и структуру папок проекта.
- Избегай поиска внешних зависимостей во время выполнения через `Find`, `FindObjectOfType` и похожие API. Обычно объявляй `[SerializeField] private` поле и связывай зависимость через Inspector. Для компонента того же объекта `GetComponent` допустим, если это упрощает решение.
- Не добавляй проверки на `null` по умолчанию для обязательных зависимостей. Если скрипт не может корректно работать без зависимости, пусть ошибка настройки проявится явно, а не будет скрыта тихим `return`. Проверяй `null` только для действительно опциональных ссылок, внешних данных или веток, где отсутствие значения является ожидаемым состоянием.

## VContainer, UniTask и DOTween

- Регистрируй зависимости VContainer в `LifetimeScope` и выбирай `Singleton`, `Scoped` или `Transient` по их реальному сроку жизни. Не разрешай зависимости через контейнер из произвольного игрового кода. Для объектов, которым нужна инъекция, используй регистрацию компонентов или создание через `IObjectResolver`.
- Передавай отмену в асинхронные операции UniTask и связывай её со сроком жизни владельца. Избегай `async void`; намеренный запуск без ожидания оформляй через `.Forget()` с обработкой ошибок. Не ожидай один экземпляр `UniTask` повторно без `.Preserve()` или другого подходящего механизма.
- Управляй сроком жизни твина DOTween вместе с его владельцем: используй `SetLink` или явно вызывай `Kill`. Для `Sequence` управляй жизненным циклом самой последовательности: `SetLink` у вложенного твина не действует. Используй `SetAutoKill(false)` только для твинов, которые действительно будут переиспользоваться.
- При интеграции UniTask и DOTween через `UNITASK_DOTWEEN_SUPPORT` учитывай, что обычный `await tween` ожидает уничтожения твина. Если нужно дождаться завершения переиспользуемого твина, используй `AwaitForComplete`.

## Unity Inspector

- Для сериализуемых полей добавляй `[Header]` только когда он помогает разделить группы в Inspector. Названия групп должны быть понятными команде.

## Работа с Unity

- Unity MCP используй только по прямому запросу пользователя на его применение. Это относится и к чтению состояния Editor, сцен и Console, и к изменению объектов, ассетов, запуску Play Mode и тестов.
- Единственный допустимый канал автоматизации Unity Editor — Unity MCP. Разрешение изменить prefab, сцену или компонент не разрешает выбирать другой канал управления компьютером.
- Запрещено использовать Computer Use, CUA, `@oai/sky`, UI Automation и другие средства управления интерфейсом компьютера для работы над проектом. Запрет относится не только к кликам и вводу: нельзя даже запрашивать список приложений/окон или снимки экрана в качестве альтернативы Unity MCP.
- Если Unity MCP отсутствует среди доступных инструментов, отключён, недоступен или не подключён к нужному Editor, немедленно останови зависимую работу, сообщи об этом и попроси пользователя включить/подключить Unity MCP. Не начинай поиск обходного канала и не заменяй MCP интерфейсом компьютера, прямой правкой YAML или автоматически выполняемыми Editor-скриптами. Независимое чтение кода и документации допустимо в пределах остальных правил.
- По умолчанию не читай YAML сцен и префабов и не назначай ссылки в Inspector самостоятельно. Сцены и настройки проекта меняй только в рамках прямого поручения пользователя; в остальных случаях дай точные шаги настройки.
- Префабы разрешено изменять через Unity MCP в рамках порученной реализации, если это даёт лучшее и более простое решение. В частности, меняй общий или базовый prefab вместо дублирования правок его экземпляров. Отдельное согласование изменения prefab в этих границах не требуется. Сохраняй GUID, ссылки, наследование и требуемое поведение всех потребителей; не добавляй обходной логический слой ради сохранения prefab без изменений.
- Запрос только на анализ, ревью или планирование не разрешает реализацию: не меняй код, prefab, сцены или настройки, если пользователь поручил лишь анализ. Прежний запрет менять prefab относился к границам такого запроса и не является общим запретом на их изменение при реализации.
- Если для реализации кода нужны сведения из сцены или Inspector, которых нет в доступном контексте, запроси их у пользователя. Не считай предполагаемые ссылки уже назначенными.
- При перемещении ассетов сохраняй соответствующие `.meta` файлы и GUID, чтобы не ломать ссылки Unity.

## Тестирование и проверка

- Проверку работоспособности в Unity Editor и на устройстве выполняет пользователь. Без его прямого запроса не запускай Play Mode, Unity Test Runner и проверки через Unity MCP.
- После изменения C# ограничь собственную проверку чтением затронутого кода и быстрыми статическими проверками, когда они доступны. Не утверждай, что компиляция в Unity или поведение проверены, если их не проверял пользователь.
- Для изменений, влияющих на Inspector, проверь по коду корректность атрибутов и сериализуемых типов; фактическое назначение ссылок оставь пользователю.
- В отчёте после задачи перечисли конкретные действия пользователя в Unity, шаги ручной проверки и ожидаемое поведение. Отдельно укажи, что ещё не подтверждено. Не отмечай задачу или Gate завершёнными, если их критерий требует ручной проверки и пользователь ещё не сообщил результат.

## Git и существующие изменения

- Не откатывай изменения пользователя без явной просьбы.
- Перед редактированием учитывай текущее состояние рабочего дерева.
- Если в файле уже есть несвязанные изменения, работай аккуратно поверх них и не переписывай файл целиком без необходимости.
- Не выполняй destructive git-команды (`reset --hard`, `checkout --`, удаление файлов) без явного подтверждения пользователя.
